# Velxio CLI 功能评估与升级计划

评估日期：2026-09-16。状态：M1 已落地（CLI-01 至 CLI-05）；M2 及以后待实施。

范围：当前工作区的 `cli/`，以及其依赖的前端工程格式、SPICE、3Dm 和后端仿真接口。工作区包含尚未提交的修改，因此本文描述当前文件状态，不代表某个已发布版本。本文只更新文档，不宣称以下升级已经完成。

## 结论

现有 CLI 已能支持目录查询、工程生成、接线、代码读写、真实编译和直流工作点计算，可作为 Agent 的工程准备入口。下一阶段应先提高输入校验、文件写入、结果契约和验收的可靠性，再实现“运行固件 → 注入输入 → 读取输出 → 断言 → 清理”的无人值守闭环。

不宜直接把现有命令数量视为完整自动化能力：`sim qemu` 尚未实现客户端；Pi 的 `compile` 返回 ready 只表示无需编译；VAP 探活成功也不表示真实模型服务可用。

## 已验证基线与证据边界

本轮评估沿用同一会话中已完成的运行验证，并补充源码检查：

- `cli/scripts/verify.sh` 返回 0，输出 42 个通过项。覆盖查询、工程操作、Kit、代码、Demo 编译、真实 SPICE 分压断言和 3Dm 转发等。
- 42 项中 QEMU 项的通过含义是正确返回不可用及退出码 2，不代表 QEMU 仿真可运行；多数编译项采用 Demo。
- 另行导出 `blink-led` 并执行不带 `--demo` 的编译，Arduino Uno 编译成功，返回 2556 字符 HEX 内容。这只证明该示例及该板型的真实编译链路。
- live `doctor` 的前端、运动视口、后端、VAP、arduino-cli、ESP32 core 六项检查均成功。VAP 返回 `mock: true`，没有真实上游配置。
- CLI 首次在受限沙箱中运行时，tsx 的本地 IPC 管道触发 EPERM；允许该本地操作后验收成功。该现象属于启动器的环境兼容性问题，不能归因于业务命令失败。
- 未验证真实 ESP32/STM32 固件运行、Pi 启动、浏览器外摄像头输入、真实模型对话、跨平台安装或并发修改工程。

现有验收包含字符串匹配和 Mock，因此上述结果是冒烟基线，不能替代完整的错误路径与协议测试。

## 优先级定义

- P0：可能写错工程、误报成功或破坏自动化判断；作为无人值守使用的前置修复。
- P1：补齐真实任务闭环，或显著提高可重复执行能力。
- P2：扩展分析深度、交互能力和分发体验。

## P0：输入与工程写入可靠性

### CLI-01 严格识别板卡与接线目标

现状与依据：

- [circuit/mutate.ts](../cli/src/circuit/mutate.ts) 的 `resolveBoard` 在显式 `--board` 未匹配时，仍回退到活动板或第一块板。拼错 ID 的 `code set` 可能写入另一块板。
- `addWire` 直接追加导线，不检查端点存在性、引脚有效性或导线 ID 重复；[validate.ts](../cli/src/circuit/validate.ts) 会检查部分端点错误，但不检查导线 ID 重复。
- [cli.ts](../cli/src/cli.ts) 的 `project init` 未在命令层限制板型，坐标仅做 `Number()` 转换；[vlxCore.ts](../frontend/src/utils/vlxCore.ts) 的解析检查主要覆盖顶层结构，仍需补充嵌套字段和引用一致性检查。

升级内容：显式板卡不存在必须报错；统一板型、有限数值、ID、端点、引脚、活动板及文件组引用校验；写入前验证修改结果。重复接线提供明确的“已存在”结果，或通过显式选项允许并行导线；不得静默追加冲突 ID。

验收条件：不存在的板卡、NaN 坐标、悬空端点、重复导线 ID 均返回结构化错误和退出码 1；失败前后原文件字节一致。多板工程中指定板卡只改变目标文件组。

### CLI-02 原子写入与并发保护

现状与依据：[ir/io.ts](../cli/src/ir/io.ts) 直接覆盖文件；`project init` 和 `example export` 也直接调用 `writeFileSync`。没有原子替换、已有目标保护或并发冲突检测。

升级内容：统一写入入口，采用同目录临时文件及原子替换；新建/导出遇到已有文件时要求显式覆盖选项；修改现有工程增加版本摘要比对或锁，避免两个进程互相覆盖。提供 `--dry-run` 与可读变更摘要。失败时清理临时文件。

验收条件：模拟写入失败不截断原文件；两个进程基于同一旧版本提交时至少一个明确返回冲突；dry-run 不改文件；正常修改保留不相关字段。

## P0：自动化结果契约

### CLI-03 统一错误、退出码和配置行为

现状与依据：

- [cli.ts](../cli/src/cli.ts) 未统一接管 Commander 用法错误；若干 catch 使用默认 `live` 信封，可能与实际 Demo 模式不符；`--format` 没有限定有效取值，`--verbose` 已声明但未用于控制日志。
- `compile` 的异常统一归为退出码 2，本地文件错误也会被视为依赖不可用；HTTP 错误通过字符串判断，不能准确区分请求、服务与编译错误。
- [env.ts](../cli/src/env.ts) 支持环境变量 Mock，但 `sim spice` 和 `doctor` 的执行分支主要依据布尔 `--demo`，可能出现输出标注 demo、实际执行 live 的不一致。doctor 的 Demo 仍会探测真实端口和本地工具。
- ADR 声明“参数优先于环境变量”，但目前未提供 API URL 等对应 CLI 参数，不能把这一描述理解成完整参数覆盖能力。

升级内容：解析一次统一的有效配置，所有模块共用；补充 `--api-url`、`--timeout` 等必要参数及参数校验；明确 Demo doctor 是纯离线结果还是诊断真实环境，并以独立选项区分。引入稳定 `error_code`、`message`、可选 `details` 与协议版本字段。保留现有 0/1/2 退出码：成功、输入或业务失败、依赖或服务不可用。帮助文本维持普通文本，其余机器模式错误统一 JSON。

验收条件：对未知命令、缺参数、坏 JSON、缺文件、编译语法错误、连接拒绝、超时建立协议测试；检查 stdout、stderr、退出码和数据来源一致。仅设置 `VELXIO_MOCK_MODE=true` 时不启动真实求解和编译；非法 format 明确失败。

### CLI-04 修正 SPICE 断言语义

现状与依据：[sim/spice.ts](../cli/src/sim/spice.ts) 对所有断言使用 `Math.abs(actual)`，不区分有符号测量与幅值；数值解析不支持负数及科学计数法，且没有严格限制电压/电流单位匹配。Demo 无夹具、无断言时可返回 `ok: true, solved: false`。

升级内容：默认保留测量符号，幅值使用显式语法或选项；支持负数、科学计数法、量纲校验及容差比较；明确区分网表生成成功、夹具断言成功、真实求解成功。由于默认符号语义变化会影响旧脚本，应同步升级协议说明并提供迁移示例。迁移：把依赖幅值的断言写成 `abs:voltage:id>2V` / `abs:current:id>5mA`。

验收条件：负电压不能通过正电压阈值断言；显式幅值断言可以通过；单位错配和非有限值被拒绝；不存在的探针明确失败；Demo 结果不能被误识别为真实求解。

### CLI-05 让验收检查结构和进程结果

现状与依据：[verify.sh](../cli/scripts/verify.sh) 大量使用子 shell 中的 `命令 | grep`。外层 `pipefail` 并不能保证每个新建 `bash -c` 都启用该行为，因此部分检查可能只观察 grep 的结果；字符串存在也不代表整体 JSON 正确。现有 parse-drive 测试应保留。

升级内容：用测试驱动器分别收集退出码、stdout 和 stderr，解析 JSON 并验证字段、结果与持久化变更。拆分离线、真实 SPICE、真实编译和真实运行四层；依赖缺失标记 skipped，不计为通过。增加上述 P0 问题的回归用例。

验收条件：故意返回非零退出码但输出成功字符串的假命令必须被判失败；重复 ID、错误板卡及环境变量 Mock 用例均纳入回归。报告分别列出 passed、failed、skipped 和运行模式。

## P1：补齐真实运行闭环

### CLI-06 仿真会话与串口

现状与依据：[sim/qemu.ts](../cli/src/sim/qemu.ts) 所有路径均返回 unavailable；后端 [simulation.py](../backend/app/api/routes/simulation.py) 已有板型相关的启动、停止、串口及 GPIO 消息，但 CLI 未封装。后端在 WebSocket 断开时会清理部分仿真实例，因此不能简单实现“start 命令退出，再由 serial 命令接管”。

升级内容：第一阶段采用前台长连接 `sim run`，在一次调用内完成启动、脚本输入、输出匹配和停止；先选可用后端上的一个板型作为垂直验收目标，再扩展 ESP32/STM32/Pi。第二阶段如需跨命令会话，再设计本地会话进程或后端持久会话协议，明确所有者、会话 ID、重连与清理规则。

必须处理：启动超时、输入节奏、UART 选择、字节与文本编码、输出缓冲、Ctrl-C、连接丢失、事件顺序和失败后的资源回收。复用后端能力，不绕过现有板型权限、镜像或容量限制。AVR 等浏览器内运行器另行评估，不能以 Arduino 编译通过推断其无头运行可用。

验收条件：一个真实固件收到指定输入并输出期望文本；进程在规定超时内结束并给出断言结果；正常结束、Ctrl-C、断线及启动失败均无遗留会话。不可用板型返回能力说明和退出码 2。

### CLI-07 编译产物和请求生命周期

现状与依据：[compile/index.ts](../cli/src/compile/index.ts) 的请求未设置明确超时，只编译活动板或第一块板，产物主要嵌入 JSON；响应未严格要求 success 和固件字段，HTTP 200 的非预期 JSON 可能被报告为成功。`firmware_b64` 还可能承载原始 HEX 文本，名称与编码不一致。

升级内容：补充 `compile --board`、明确超时和取消、`--out-dir`；验证响应结构与板型所需产物，输出文件路径、格式、编码、摘要及编译元数据。兼容期保留旧字段并标记弃用。多板批量编译作为后续选项，不默认启动所有板卡编译。Pi 保留“无需编译”的独立状态。

验收条件：后端挂起可超时退出；空响应或缺产物不能成功；HEX 与 Base64 字段含义一致；输出产物可供 CLI-06 加载；选择不存在的板卡失败；取消编译的服务端行为需明确记录。

### CLI-08 可重复的工程编辑

现状与依据：当前命令可增删元件和导线，但缺少直接修改元件参数、位置、旋转以及板卡增删切换的完整入口；多步修改逐条写文件，无法整体回滚。

升级内容：提供 `circuit set`、板卡管理和声明式 `project apply`；复用现有元件属性及板型真源，支持 dry-run、差异预览、整体校验和一次提交。明确幂等规则，失败则整批不落盘。批量输入使用 JSON 文件，减少复杂 shell 转义。

验收条件：同一操作集重复应用，除允许的时间戳外结果一致；中间操作失败不留下半成品；电阻值、LED 属性、舵机参数等可按元数据更新；生成工程能由编辑器导入并保持代码、属性与接线。

### CLI-09 能力发现与分层探活

现状与依据：[doctor.ts](../cli/src/doctor.ts) 固定检测 5173/5174，live 成功仅要求 backend 和 VAP；ESP32 core 只检查存在性，没有完整版本和板型运行能力判断。VAP Mock 健康与真实上游可用不是同一概念。

升级内容：新增机器可读 capabilities，按板型列出 compile、run、serial、GPIO、SPICE 等能力及不可用原因；doctor 增加 compile/sim/vap 等检查范围和可配置地址。区分服务可达、依赖就绪和真实任务验证；真实模型调用另设显式检查，避免普通探活产生调用成本。

验收条件：缺少某个模拟器时只影响相关能力；Mock 服务不会被标为真实模型就绪；版本要求和缺依赖原因可操作；指定检查范围的退出码由该范围决定。

## P2：分析与集成扩展

### CLI-10 更完整的 SPICE 分析

目前 [sim/spice.ts](../cli/src/sim/spice.ts) 固定 `analysis = { kind: 'op' }`。按求解器实际能力分期增加瞬态、交流扫描、时间窗口及 CSV/JSON 导出，明确采样单位与误差容限。验收使用已知 RC 波形或频响，并与理论值及共享求解器结果对照。

### CLI-11 VAP 和浏览器能力边界

VAP/Studio 当前侧重清单、探活和布局查询。先建立可重复的文本、传感器和预录制图像输入通道；实时摄像头、麦克风、浏览器画布和 3D 展示继续明确标为交互能力。确需无头视觉/语音时再设计文件输入协议及 HostBridge 适配，不以 UI 点击自动化替代 CLI 协议。验收分别验证 Mock 与配置好的真实服务，不混计通过数。

### CLI-12 启动和分发体验

当前 [启动器](../cli/bin/velxio) 依赖 Bash、Python、tsx 及仓内源码；[package.json](../cli/package.json) 为 private，CLI 跨目录直接引用多个包，不能视为独立可安装产品。

先试验不依赖 tsx CLI IPC 的启动方式或预编译入口，再评估 Node 单入口和发布包；保留与前端共用目录、Kit、IR 和求解器真源，避免复制注册表。补充支持的 Node/操作系统版本和干净环境安装验收。标准输出 byte 字段改为 UTF-8 实际字节数；3Dm 转发补测带等号参数、退出信号及格式继承。

## 实施顺序与交付门槛

以下为单名熟悉代码的工程师的初步有效开发工作日估计，不是发布日期承诺；模型、镜像、跨平台环境和后端会话改造可能增加工作量。

1. **M1 可靠性基线，约 5–8 日（已完成，2026-09-16）**：CLI-01 至 CLI-05。验收：`cli/scripts/verify.sh` 在本机 Darwin 上 **passed=71 failed=0 skipped=2**（compile-live / run-live 按计划跳过）。日志：`cli/logs/verify.log`。spice-live 分压断言通过；真实多板编译与 `sim run` 仍未承诺。
2. **M2 单板真实闭环，约 6–10 日**：CLI-07、CLI-09 和 CLI-06 的前台会话。先确认可用板型及固件协议；门槛为真实编译或载入产物、运行、串口断言及清理全部完成。持久会话暂不作为本阶段承诺。
3. **M3 工程批处理，约 4–6 日**：CLI-08；扩展多板选择及重复执行验收。门槛为幂等应用、失败回滚、编辑器往返兼容。
4. **M4 按需求扩展，另行估算**：CLI-10 至 CLI-12、更多板型以及持久会话。每项单独证明底层能力后再承诺时间，不以统一“全功能支持”验收。

关键依赖：CLI-02/03 是 CLI-08 的基础；CLI-03/05/07/09 是 CLI-06 的基础；CLI-04/05 应先于更多 SPICE 分析类型。修复与新增协议建议拆成独立可审查变更。

## 拟议命令示例（尚未实现）

以下用于明确交付行为，不可直接作为现有命令执行；参数命名以实现评审为准。

```bash
velxio capabilities --board esp32 --format json
velxio doctor --scope compile --board esp32
velxio project apply -p robot.vlx --operations changes.json --dry-run
velxio compile -p robot.vlx --board esp32 --out-dir ./build --timeout 120s
velxio sim run -p robot.vlx --board esp32 --scenario serial-check.json --timeout 30s
```

运行场景文件应声明固件来源、启动就绪条件、串口输入、输出断言和超时。`sim run` 结束前清理连接与仿真实例；事件流采用单独声明的 NDJSON 模式，单次命令保留单 JSON 结果，避免破坏现有解析脚本。
